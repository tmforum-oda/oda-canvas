# RI Developer README

This README is for people who build or help to fix/debug RIs that support the CTKs. It explains how to run and develop the RI. It will NOT be shipped with the RI for members to read.

When the RI is built for delivery, a generic README.md file will be shipped. This will explain how to run the RI for investigation and testing purposes.

## Overview

This RI server was generated using the [OpenAPI Generator](https://openapi-generator.tech) project. The generator and its output enable an API-first approach: the API contract is the anchor for your project, and your code and business logic aim to comply with that contract.

The primary purpose of the RI is to deliver a set of sunny-day results for the tests listed and executed in the accompanying CTK.

The code was written on a Mac, and should work smoothly on Linux-based systems. There is no reason it cannot run on Windows. If you encounter an OS-related issue, please open an issue and we’ll address it.

---

### Running the server with Docker (preferred approach)

#### Prerequisites
- **Docker Desktop** installed and running
- On **Windows 11**:
  - Virtualization enabled in BIOS
  - WSL 2 installed and set as default

To run the server using Docker, navigate to the RI root directory and run:

```bash
docker compose up
```

### View and test the API

Open: `http://localhost:8620/tmf-api/xxxxxxxxxxxx/v5/api-docs/`

In some environments you may need to use 127.0.0.1 instead of localhost

You can browse the API documentation and test available endpoints. 

> Note: At this stage, the server does not support request bodies sent in XML. Form submissions will be supported in the near future.


### Connect to the embedded MongoDB database

During development it is often useful to connect to the MongoDB database used by the RI to inspect data.

This is done by exposing a port in the Docker Compose file:

```bash
 mongo:
    image: mongo:4.4.6
    ports:
      - 27017:27017
```

### Connect a debugger to the RI

During development it is often useful to connect a remote debugger to the RI. 
In VS code this is done by configuring the launch.json file in the .vscode directory at the root of the repository.

An entry such as the following is needed:

```bash
 {
            "type": "node",
            "request": "attach",
            "name": "Attach to Docker Node TMF648 RI",
            "address": "localhost",
            "port": 9648,
            "localRoot": "${workspaceFolder}/apis/TMF648-Quote/ri",
            "remoteRoot": "/app" 
  }
```

Note the port and the /apis/TMF648-Quote/ri code reference.

### Build the server code from an OAS file

A docker-compose file is provided under the generator folder. Copy the OAS file you wish to generate code for into the root directory and run the Docker image:

```bash
docker compose up
```

The generated files will be placed in the 'generated' folder of the docker-compose file. Once generated, some bespoke development will be required to store and retrieve requests and responses from the embedded MongoDB database, so that the CTK tests can complete the full POST–GET–PATCH–DELETE lifecycle in accordance with the operations defined in the API’s OAS file and Conformance Profile.
Copy an existing project and make changes as necessary.


### Node version and guidelines

This code was written against Node.js 10.6 and follows the [Airbnb ESLint style guide](https://github.com/airbnb/javascript).

## Project Files

### Root directory
Besides `package.json`, `config.js`, and log files:

- **`logger.js`** — Defines the project logger (Winston by default) and provides a single place to customize logging behavior.
- **`index.js`** — The project’s entry point. Kept deliberately minimal so the server can be launched with different parameters (e.g., config and/or logger) without impacting the rest of the code.
- **`expressServer.js`** — Initializes the Express server, the OpenAPI validator, the OpenAPI UI, and other required libraries. This is where you would add external links/integrations. The project uses [`express-openapi-validator`](https://www.npmjs.com/package/express-openapi-validator), which intercepts requests to paths defined in `openapi.yaml`, validates parameters and body content against the schema, and—on success—adds an `openapi` object to the request. Requests to paths not defined in `openapi.yaml` are passed through unchanged.

### `api/`
- **`openapi.yaml`** — The OpenAPI contract this server adheres to. Generated by codegen and intended to be self-contained (no external schema references).

### `utils/`
- **`openapiRouter.js`** — Routes validated requests to backend code. If the request includes an `openapi` object, it reads the `x-openapi-router-controller` and `x-openapi-router-service` values (from `openapi.yaml`) and the `operationId`. It sends the request/response objects to the appropriate controller, which extracts variables and calls the corresponding service, returning the service response to the caller.

### `controllers/`
After validation, requests are sent to a controller, which extracts variables/parameters and hands them to the relevant service. The controller then builds the HTTP response from the service result.

- **`index.js`** — Loads all generated controllers and exports them for dynamic use by `openapiRouter.js`. If you customize a controller, link to it here and ensure codegen does not overwrite this file.
- **`Controller.js`** — Core logic shared by generated controllers: parses request variables/arguments and builds HTTP responses. Implemented as a class with static methods.
- **`{{x-openapi-router-controller}}.js`** — Auto-generated controller handling all operations. Each operation in `openapi.yaml` has an `operationId`, which maps to a controller method. Methods receive the request/response, then delegate common processing to `Controller.js` and call the appropriate service method for business logic.

### `services/`
This is where your application’s business logic lives. Each endpoint in `openapi.yaml` specifies `x-openapi-router-service`, the name of the generated service class. The endpoint’s `operationId` maps to a method on that service.

- **`index.js`** — Loads all generated services and exports them for dynamic use by `openapiRouter.js`. If you customize a service, link to it here and ensure codegen does not overwrite this file.
- **`Service.js`** — A thin utility with static methods to build success and error responses (defaulting to HTTP 200 for success and 500 for failure). Override defaults where appropriate.
- **`{{x-openapi-router-service}}.js`** — Auto-generated service stubs: each method corresponds to an `operationId` in `openapi.yaml`, wraps logic in a Promise with try/catch, and uses `Service.js` to produce the final response.

### `tests/`
- **`serverTests.js`** — Basic server validation: ensures the server starts; an in-scope endpoint returns 200; a request to an out-of-scope path returns 200 if it exists or 404 otherwise.
- **`routingTests.js`** — Iterates all endpoints in `openapi.yaml`, builds a dummy request per endpoint, and expects a 200 response. Requests containing XML or `formData` currently fail (not yet supported in the router).
- **`additionalEndpointsTests.js`** — Tests endpoints defined outside the OpenAPI scope and expects 200 responses.

Future tests should verify that every response conforms to the structures defined in `openapi.yaml`. These will initially fail until the implementation is complete.

### `models/`
Currently a concept awaiting feedback. The idea is to treat objects defined in `openapi.yaml` as models passed between modules. This encourages interaction via well-defined objects rather than loosely defined JSON. Given typical JavaScript development practices, this may or may not be desirable; leaving this here for discussion and feedback.
